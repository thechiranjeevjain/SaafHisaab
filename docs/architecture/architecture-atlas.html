Authorization sequence

Authentication identifies an account. Authorization separately proves that account belongs to the selected homeowner-worker pair.

Current
sequenceDiagram
  autonumber
  actor U as Homeowner / worker
  participant C as APK / web client
  participant D as dispatch_()
  participant A as authenticateAccount_()
  participant P as authorizePair_()
  participant S as Sheets repository
  U->>C: Phone + PIN
  C->>D: login
  D->>S: Read normalized account
  D->>D: Verify salted hash + rate limit
  D-->>C: Session token + authorized pairs
  U->>C: Select one relationship
  C->>D: action(token, pairId, payload)
  D->>A: Validate hashed session
  A->>S: Load active account
  D->>P: Verify account in pairId
  P->>S: Load relationship
  alt permitted member and role
    P-->>D: actor with userId, pairId, role
    D->>S: Read/write this pair only
    D-->>C: Pair-scoped snapshot
  else outsider or missing pair
    P-->>C: Access denied
  end

Homeowner authority

Writes canonical activity records, classifies no-contact absence, accepts requests, sees internal rates, and locks final payment.

Worker authority

Reads the shared ledger, submits structured requests, confirms or disputes homeowner entries, and acknowledges payment—without direct payroll writes.

Salary state flow

Confirmed pay is intentionally stable. Pending records produce a separate projection and cannot silently deduct salary.

Current
flowchart TD
  IN[Logs + policy + selected month]:::input --> APPROVAL{Approval state}:::decision
  APPROVAL -->|confirmed| CONF[Confirmed set]:::good
  APPROVAL -->|pending| PEND[Pending set]:::warn
  APPROVAL -->|disputed| DISP[Excluded]:::bad
  CONF --> VALUE[Convert leave / misses to value]:::calc
  ALLOW[Paid leave days × daily rate]:::calc --> ADJUST[Adjustment = max 0, used − allowance]:::calc
  VALUE --> ADJUST --> PAY[Confirmed current pay]:::good
  PEND --> PROJECT[Projected pay if accepted]:::warn
  PEND -. never changes .-> PAY

Why this technology stack

The chosen stack optimizes pilot delivery, code reuse, and operating cost—not unlimited concurrency.

DecisionWhy chosen nowWhat we give upRevisit signal
Vanilla JSTiny dependency surface; current UI is manageable; portable salary functions.No component framework or typed compiler boundary.UI/state complexity creates repeated defects.
CapacitorOne web/Android codebase and access to native sharing.WebView limits for deep Android behavior.Offline/background/native capabilities become core.
Apps ScriptNo server operations; integrates directly with Sheets and Drive.Quotas, execution limits, cold-start variability, limited observability.Measured latency, quota, or support pressure.
Google SheetsFree pilot ledger, owner visibility, easy setup and export.No real relational transactions or efficient high-volume querying.Cross-tenant reporting, concurrency, or compliance.
Phone + PINNo SMS fee; simple for controlled users.No verified phone possession; limited recovery/revocation.Public launch or higher-risk payroll.
JSON.gzCompact, versioned, portable, migration-friendly.Admin restore is coarse-grained and owner-operated.Need point-in-time or self-service restore.

Portable foundations

Pair-scoped identity, pure salary functions, versioned exports, shared UI assets, and an explicit API dispatcher can survive a backend replacement.

Known ceilings

Whole-sheet scans, owner-account dependence, custom PIN recovery, Apps Script quotas, and localStorage caching are pilot boundaries.
